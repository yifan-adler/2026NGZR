# src1.6.3：区间评分门控与统一平台期限

基线为独立 `src1.6.2`；原版本、官方 SDK 与原题不改。最终回归结果见 `../test-results/validation-20260927/REPORT.md`、summary.json 与 performance.json。

## 06 定位及修复

固定外部种子 20260927，先复跑 1.6.1/1.6.2：06 IT 与 NT 各三轮均为 302 → 259。1.6.2 将历史 UNKNOWN 约束的确定资格分移出 lower bound；原 tradeoff 又对 UNKNOWN 在投影后变确定的目标/约束额外减分，继续把结果当作精确收益比较。检查阶段 task 1 的相关组在 1.6.1 获准，在 1.6.2 被阻断；少完成目标不是解析或新动作策略造成。

新版本将两套量明确分开：ScoreEvaluator/TerminalChecker 仍按 1.6.2 官方语义给出确定下界和可能上界；冻结的 LegacyPriorityChecker 仅重现 1.6.1 的谓词启发式，用于守约优先、相关组和分阶段延后。它不是计分真值或区间，不能作为评分硬淘汰的证明。仅在 `loser.possible_base_score < winner.deterministic_base_score` 时允许评分硬淘汰；对照方案须完整、可执行且能按期限完成。接触和重叠区间仍按 legacy 优先级延后/重评，任务不会因此被禁用或标为完成。

guarded 替换 legacy、选择组后停止，以及直接停止，都要求确定下界严格超过参考方案的可能上界。授权重放同时核对 lower 和 upper。guarded 仍仅支持原 Stage 1；beam 排序仍是既有搜索启发式，资源裁剪不代表评分支配证明。

开发中“区间重叠就立刻执行”的原型使 06 降到 167，已弃用；它说明宽松上界不能用来改变既有决策优先级。恢复 legacy 优先级后，在原时间配置下 IT/NT 均回到 302；最终按用户补充要求改为统一 5000 ms，再重跑全部验收，结果以最终报告为准。

## 29 定位及时间修复

初次 1.6.1/1.6.2 三轮重复：1.6.1 均 856，1.6.2 为 788、856、856。降分时缺少尾部 `Move(13)/PickUp(13)/Move(7)/PutDown(13)`，是动作前缀差异。诊断表明新增评分/投影工作为毫秒级，同步 SDK 动作调用约为秒级；不能将整组尾部遗漏都归因于评分 CPU。

更直接的问题在于 dry-run：当预计动作累计耗时超过剩余预算时，它可能只记录 0 或 3 个动作并中断，而原 CanStartPlan 仍按该不完整序列放行。实际执行可以包含全部 4 个动作；空预览也可以通过零耗时门槛。另有重复的零动作搬运项在 300 ms 边界阻断整段循环，造成基线的尾部有时执行、有时遗漏。

单任务投影现在完整记录同一动作序列，实际准入拒绝不完整投影。主循环、投影、guarded、尾部和 deadlineReached 统一引用默认 5000 ms 平台上限，取消独立 4700 ms 截断。普通完整计划保留 300 ms 余量；既定尾部完整计划保留 100 ms 输出余量，均只扣一次。实际剩余墙钟不足仍拒绝计划；没有新增目标、动作或搜索分支。

性能优化只复用同一状态下刚算出的 TerminalSummary，不建立跨状态缓存；动作后资格更新仅枚举约束，省去无用目标评分。阶段诊断默认关闭，开启时使用固定计数器、无逐动作输出；汇总包括终态、绑定、账本、投影、候选、tradeoff、guarded、平台调用和 tail。阶段时间含嵌套，不能相加。

## 验证范围

最终结果：86 对 guarded 官方配对中 83 对基础分与动作完全相同、3 对提高、0 对降低；所有评分有效、0 硬超时、0 动作成本不匹配。06 IT/NT 均为 259→330（6→10 目标，5→3 约束，81→130 成本），动作在原前缀后多执行四项既有搬运；28 NT 为 748→816（多完成两项目标）。29 IT/NT 本轮均为 856，动作序列一致。默认 off 14 对全部同分、同动作。

06 IT/NT、29 IT 各 5 轮交替顺序配对：06 每轮 259→330，29 每轮 856；关闭诊断的各 3 轮也分别为 330 / 856。最终接受的官方运行共 239 次（172 全量 + 28 off + 30 定向 + 9 诊断关闭），全部有效，无平台硬超时。基线本地/官方语义 10/10、基线 sanitizer 9/9；新版本本地/官方语义 11/11、新版本 sanitizer 10/10 通过。16 个官方评分语义案例全部通过。

29 的同种子五轮计时中位数：终态枚举 8.675→5.233 ms，约束账本更新 1.948→0.094 ms，完整投影 7.653→6.066 ms；终态全量检查约 690→443 次。新版本虽完整记录尾部计划，并在统一期限后增加一次末段候选检查，仍减少了评分 CPU。各阶段含嵌套，不能相加。同步平台动作调用中位数 4.736→4.731 s，49 次动作调用，说明主墙钟成本在平台调用。诊断开启时新版本 29 Plan 墙钟为 4.721～4.757 s，关闭时为 4.741～4.779 s；系统/平台抖动大于计时开销，不能用两组墙钟中位数之差推断诊断“负开销”。

58 个 Stage 1 配对的内部基础分全部与官方一致；Stage 2 仍有保守低估，06 最终内部下界 270、官方基础分 330。最终全量没有发现内部下界超过官方基础分，不能据此把下界当成精确收益。

原 1.6.2 的本地、16 案例官方语义、sanitizer、86 对 guarded 官方配对及 14 对默认 off 路径全部复跑；新增测试覆盖重叠/相接/严格支配、不可执行 incumbent、legacy 延后不禁用任务、同状态评分复用、短预算完整投影和不完整投影拒绝，以及默认 5000 ms。另对 06 IT/NT、29 IT 各做 5 轮交替顺序定向配对，并做关闭诊断的重复运行。

源码和 SDK 构建哈希、原题哈希、动作差异、官方终态、原始日志和耗时统计保存在版本内证据目录。尚不能消除 Stage 2 的观测/绑定/历史不确定性；lower bound 不应当成官方精确收益。执行耗时仍受系统负载影响，所测无硬超时不构成未来任意负载下的保证。
